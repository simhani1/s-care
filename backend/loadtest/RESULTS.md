# 동기(2024) 구조 대 큐 구조 부하 비교

2024 서버(AWS t2.xlarge)의 계산 속도에 맞춘 CPU 예산으로, 2024 동기 구조와 현재 큐 구조를 같은 머신에서 부하 시험한 결과다.

**인용할 때의 표현.** 아래 수치는 2024 서버에서 잰 값이 아니다. 2024 기록(심박 1,300개 누적 계산 22초)에 맞춰 보정한 재현 환경을 2026년에 다른 하드웨어(Apple M4 Pro, Docker Desktop)에서 돌린 값이다. "2024 측정치에 맞춰 보정한 재현 환경에서" 라고 쓰면 정확하다.

## 1. 핵심 수치: 큐 구조가 버티는 동시 사용자 수

### 1.1 예산 정의 (t2.xlarge 기준)

| 이름 | 뜻 | 계산기 컨테이너 | 2024 누적 계산, 심박 1,300개 |
|---|---|---|---|
| 크레딧 있음 | t2.xlarge 의 Xeon 1코어 속도(이 Mac 의 약 1/5.5) | `--cpus 0.28` | 4.3–4.7초 |
| 크레딧 소진 | vCPU 마다 기준 성능 22.5%로 제한 | `--cpus 0.12` | 19.9–21.4초 (기록 22초) |

22초가 기록될 때 서버가 크레딧 소진 상태였다는 것은 수치에서 나온 추론이다. 측정 근거: 이 Mac 에서 같은 코드가 0.68–0.90초, pyhrv 버전과의 비율로 본 Xeon 1코어는 약 5.5배 느리므로 4–5초, 그 22.5%는 18–22초다. 재현 환경에서 두 예산의 비율은 4.6배로 t2 의 1/0.225 = 4.4배와 맞는다. 22초 측정 전에 돌린 96초짜리 pyhrv 계산들이 크레딧을 소진시켰을 가능성이 크다.

### 1.2 같은 순간에 N명이 M분 산책을 마칠 때, 마지막 사람의 결과가 나오는 시간 안에 들어오는 최대 N (큐 구조)

### 1.5 22초인데도 60초 제한 뒤에서 실패한 이유 (크레딧 소진, 2024 누적 계산, 동기)

| 조건 | 실측 |
|---|---|
| 22분 산책(심박 1,320개) 1건 | 22.0초, 결과 있음 |
| 22분 산책 2건 동시 | 둘 다 60.1초에 504, 둘 다 스트레스 없이 저장. 계산기만 따로 재면 2건 각각 66.2초, 66.8초 |
| 22분 산책 3건 동시 | 셋 다 60.0초, 결과 없음 |
| 10 / 20 / 30분 산책 1건 | 5.2 / 16.0 / 33.8초 |
| 35 / 37분 산책 1건 | 43.0 / 50.4초 |
| 40분 / 60분 산책 1건 | 60.1초에 504, 결과 없음 (큐 워커에서 60분은 128초 걸려 결과가 나옴) |

- 길이: 누적 계산은 샘플 수의 제곱에 비례한다. 단독 요청도 약 38–39분 산책부터 60초를 넘는다.
- 동시성: 2024 계산기는 단일 프로세스의 `def` 라우트라 동시 요청이 스레드로 GIL 을 나눠 쓴다. k건이 동시에 들어오면 각각 k배보다 더 느려졌다. 2건 3.1배(22분, 소진 예산), 3건 7.7배(30분 윈도우, 소진 예산). 이 Mac 에서 제한 없이 돌려도 3건 5.7배라 컨테이너 제한의 부작용만은 아니다. 22분 산책 두 명이 겹치기만 해도 둘 다 결과를 잃는다.
- 앱 쪽: 안드로이드 `ApiService` 는 OkHttp 기본 읽기 시간 제한(10초)을 그대로 쓴다. 코드로 본 추론이지만, 서버가 22초 만에 결과와 함께 저장해도 앱은 10초에 시간 초과를 받았을 것이다. 위 동기 실측의 저장 응답은 대부분 10초를 넘었다.
- 2024 동기 구조의 마지막 커밋(95be6d1^)은 실제로는 pyhrv 버전(1,300개 96초)을 쓰고 있었다. 누적 계산을 수기 구현으로 바꾼 커밋(95be6d1)이 RabbitMQ 도입과 같은 커밋이다. 동기 + 수기 누적 계산 조합은 843e363(2024-11-11)에서 5d1b5fe(11-12) 사이에만 있었다. 이 문서의 "2024 동기"는 그 조합이다. pyhrv 였다면 단독 요청도 60초를 넘는다(96초, 계산이며 재지 않았다).

**권장: 3초 간격으로 묻고, 60초가 지나면 폴링을 멈추고 "분석 중" 으로 둔다.**

- 현재 계산(윈도우), 워커 1대에서 단건 결과는 크레딧 있음 2.3–11.4초(p50 8.1), 크레딧 소진 6.9–18.2초(p50 15.0)였고, 0.5–1배 유입에서도 최대 19.3초였다. 지연은 대부분 릴레이 대기(0–10초. Spring 로그로 잰 40건에서 0.4–9.9초)와 계산 시간이다.
- 간격: 결과가 생긴 뒤 화면에 뜨기까지 평균 간격의 절반만큼 늦는다. 3초면 평균 1.5초 늦고(p50 8초의 약 20%) 산책 한 건에 조회 3–7회다. 1초 간격은 조회가 3배인데 줄어드는 지연은 평균 1초다. 더 빠르게 하려면 릴레이를 1초로 줄이는 쪽이 낫다(p50 8.1초 → 2.3초, 3.5절).
- 60초: 정상 범위에서 잰 최대(19.3초)의 약 3배다. 60초를 넘기는 것은 1배를 넘는 유입(2배 유입에서 최대 104–118초)이나 워커 장애다. 이때도 결과는 사라지지 않으므로, 화면은 분석 중으로 두고 목록과 상세에서 나중에 보이면 된다(`analysisStatus`). 계속 묻는 것은 장애 때 부하만 늘린다.
- 2024 누적 계산이었다면 크레딧 소진 단건이 p50 36초, 최대 41초라 60초 안이지만, 동시 3명이면 마지막 결과가 100초라 넘는다.

## 2. 환경과 방법

| 항목 | 값 |
|---|---|
| 머신 | Apple M4 Pro, Docker Desktop VM 8 CPU / 8 GB |
| 계산기 | `backend/fast-api` 이미지(Python 3.12.2). 큐 워커는 `main.py`, 동기 계산기는 `sync_app.py`(벤치 브랜치). `--cpus` 로 제한 |
| 동기 구조 | 2024 `WalkingCommandService` 복원: `@Transactional` 안에서 RestClient 동기 호출, `RestClientException` 이면 스트레스 없이 저장. Nginx(`proxy_read_timeout 60s`) 뒤 계산기. `bench/sync-baseline` 브랜치 |
| 큐 구조 | 현재 main 그대로(아웃박스, 릴레이 10초, prefetch 1, 내부 저장 API). 벤치 브랜치에서 워커 계산만 `STRESS_ALGO=prefix` 로 바꿀 수 있다 |
| Spring, MySQL, RabbitMQ | 호스트 프로세스와 컨테이너, 제한 없음 (4절 변형만 제한) |
| 부하 | `bench.py`, 열린 루프(응답이 늦어도 정해진 시각에 보냄). 합성 심박(초당 1개), 좌표 같은 수. 클라이언트 시간 제한 200초 |
| 동시 관찰 | 0.5초마다 Hikari 활성/대기, Tomcat 바쁜 스레드. 1초마다 `GET /api/v1/walking/list` |
| 결과 판정 | 동기: 응답 시점에 `COMPLETED` 면 결과 있음. 큐: 코스가 `ANALYZING` 을 벗어날 때까지 대기 |

## 5. 큐가 준 것과 치른 것 (측정 근거만)

준 것
- 결과 유실 0. 동시 저장, 1배를 넘는 유입, 계산기 무응답과 중지 모두에서 저장한 산책은 전부 결과를 받았다. 동기 구조는 같은 조건에서 대부분 결과를 잃었다(1.4절, 3.2–3.3절).
- 저장 응답이 계산과 분리됐다. 큐는 모든 시나리오에서 저장 0.1초 안팎(상자 예산 변형 2.2초 이하), 실패 0건. 동기 구조는 결과가 없을 때에도 사용자가 60초를 기다렸고, 앱 시간 제한(10초)을 넘는 응답이 대부분이었다.
- 장애 반경. 동기 구조는 계산 지연이 DB 커넥션 풀을 막아 무관한 목록 조회까지 실패시켰다(동시 10건부터). 큐 구조에서 DB 활성 커넥션은 최대 1–2였고 목록 조회 실패 0건.
- 복구. 동기 구조는 계산기 무응답 뒤 복구돼도 버려진 계산이 남아 회복되지 않았다. 큐는 쌓였다 처리됐다.

치른 것
- 부하가 낮을 때 결과가 늦다. 단건과 0.5배 유입에서 동기 구조는 계산 시간만큼(크레딧 있음 윈도우 30분 2.0초) 걸렸지만, 큐는 릴레이 대기 0–10초가 더해졌다(같은 조건 p50 8.1초). 릴레이 1초로 줄이면 p50 2.3초.
- 결과가 늦게 오므로 클라이언트가 분석 중 상태를 보여주고 다시 물어봐야 한다(폴링).
- 움직이는 부품이 늘었다. RabbitMQ, 아웃박스 테이블과 릴레이 스케줄러, 내부 저장 API 와 공유 비밀, 데드레터 큐, 실패 처리 스케줄러. 이번 측정 중에도 워커 구독 확인과 관리 API 지연 같은 문제를 다뤄야 했다.
- 처리량은 늘지 않는다. 같은 CPU 에서 계산 속도는 같다. 큐는 몰린 요청을 줄 세울 뿐이고, 1배를 넘는 유입이 계속되면 결과 지연이 끝없이 늘어난다(크레딧 있음 5배 120초 유입에서 마지막 결과 455초). 계산이 느린 문제 자체는 윈도우 계산 교체가 줄였다(30분 산책 소진 예산 35초 → 9.5초).

## 6. 한계

- ARM(M4 Pro) 대 2024 x86(Xeon Haswell/Broadwell). 명령어 수준 차이는 재현하지 않았다. 계산 시간 하나만 맞췄다.
- 보정 근거는 22초라는 기록 하나다. 크레딧 있음 예산은 pyhrv 비율에서 나온 추정이다.
- `--cpus` 제한은 VM 부하에 따라 컨테이너당 속도가 달라진다. 같은 0.12 에서 누적 1,300개가 혼자 돌 때 15.6–16.0초, 2개 동시 13.1–13.8초, 4개 동시 8.1–12.6초였다(세션 막바지 측정). 같은 단독 측정도 세션 초반 19.9–21.4초에서 막바지 15.6–16.0초로 바뀌었다. 단일 워커 결과는 보정과 같은 조건이지만, 다중 워커 결과는 예산보다 빠르다.
- 동기 구조의 GIL 경합 배율(3건 7–8배)은 Linux 컨테이너에서 이 Mac 직접 실행(5.7배)보다 컸다. 2024 Xeon 에서의 배율은 모른다. 2건 동시 실측은 계산기 단독 3.1배였고, 단순 2배만 가정해도 22분 2건은 44초씩이라 60초 안이지만 3건(66초)은 넘는다.
- 크레딧 적립과 소진의 시간 변화, EBS 디스크 I/O, Nginx·Spring·FastAPI 사이 네트워크 홉, 같은 서버의 다른 부하(Jenkins 빌드, MongoDB, Redis)는 재현하지 않았다.
- 본 측정에서 Spring, MySQL, RabbitMQ 는 제한하지 않았다(4절 변형 제외). 부하 생성기도 같은 머신에서 돌았다.
- 2024 Nginx 설정은 저장소에 없다. 60초 upstream 제한은 전달받은 사실이다. POST 는 다른 upstream 으로 재시도하지 않는 Nginx 기본값을 썼다.
- 합성 심박(105 ± 8 사인파 + 잡음)이다. 계산 시간은 값보다 개수에 좌우된다.
- 큐 측정 일부는 워커가 구독을 마치기 전에 발행돼 결과 지연이 최대 약 10초 부풀었다(측정 도구 문제, 큐에 불리한 방향). 고친 뒤 다시 잰 값이 있는 곳은 그 값을 썼다(1.3, 1.6절).
- 측정 중 맥이 잠들었던 구간(22:49–23:16)의 단건 측정은 버리고 다시 쟀다.
