# 산책 저장 고도화 PR 진행

스펙의 PR 하나를 끝까지 진행한다. 구현과 검증을 서로 다른 에이전트가 맡는다. 구현자가 자기 코드를 검증하면 같은 가정을 반복하기 때문이다.

**실행 모드:** 서브 에이전트. 작업이 순차 의존이고 에이전트가 둘뿐이라 팀 통신이 필요 없다. 결과는 파일로 주고받는다.

## 에이전트

| 에이전트 | 정의 | 역할 |
|---|---|---|
| implementer | `.claude/agents/implementer.md` | 스펙의 PR 범위 구현 |
| verifier | `.claude/agents/verifier.md` | 스펙 대조, 경계면 비교, `e2e-verify` 실행 |

Agent 도구로 부를 때 `model: "opus"` 를 명시하고, 프롬프트에 해당 정의 파일을 읽으라고 적는다.

## 절차

### 0. 컨텍스트 확인

- `docs/spec/walk-save-improvement.md` 5장에서 대상 PR 과 선행 PR 을 확인한다. 선행 PR 이 main 에 병합되지 않았으면 진행하지 않는다.
- `_workspace/` 를 본다.
  - 대상 PR 의 산출물이 있고 부분 수정 요청이면 해당 에이전트만 다시 부른다.
  - 대상 PR 의 산출물이 있고 처음부터 다시 하라는 요청이면 `_workspace_prev/` 로 옮기고 새로 시작한다.
  - 없으면 초기 실행이다.

### 1. 브랜치

최신 main 에서 브랜치를 만든다. 접두사는 기존 커밋 관례를 따른다(`feat/`, `fix/`, `refactor/`, `chore/`).

### 2. 구현

implementer 를 부른다. 입력은 PR 번호와 브랜치다. 산출물은 `_workspace/{PR}_implementer_summary.md`.

### 3. 검증

verifier 를 부른다. 입력은 PR 번호, 브랜치, 구현 요약이다. 산출물은 `_workspace/{PR}_verifier_report.md`.

### 4. 반려 처리

반려면 implementer 를 다시 불러 보고서의 항목을 고치게 하고 3단계로 돌아간다. 두 번 반려되면 멈추고 사용자에게 쟁점을 보고한다. 같은 지적이 반복되면 스펙이나 접근이 틀렸을 가능성이 높다.

### 5. PR 생성

통과하면 커밋하고 PR 을 올린다.

```bash
gh pr create --repo simhani1/s-care --base main --head <브랜치> --title "<제목>" --body "<본문>"
```

`--repo` 를 빼면 원본 저장소 `S-Care/s-care` 로 올라간다. 본문에는 배경, 변경 사항, 검증 결과(실행한 명령과 출력), 검증하지 못한 것을 적는다.

**병합하지 않는다.** `gh pr merge` 를 실행하지 않고 PR 링크를 사용자에게 주고 멈춘다. 사용자가 코드를 리뷰하고 직접 병합한다. 다음 PR 은 사용자가 병합을 알려준 뒤에 시작한다.

### 6. 스펙 갱신

구현 중 스펙과 달라진 결정이 있으면 같은 PR 에서 스펙 문서를 고친다. 스펙이 낡으면 다음 PR 의 기준이 사라진다.

## 데이터 흐름

```
스펙 5장 ─▶ implementer ─▶ _workspace/{PR}_implementer_summary.md
                                      │
                                      ▼
                               verifier ─▶ _workspace/{PR}_verifier_report.md
                                      │
                         통과 ◀───────┴───────▶ 반려 (implementer 재호출)
```

`_workspace/` 는 git 에서 무시된다. 감사 추적용으로 지우지 않는다.

## 에러 핸들링

| 상황 | 처리 |
|---|---|
| 에이전트가 산출물 없이 끝남 | 한 번 다시 부른다. 또 실패하면 멈추고 보고한다 |
| 로컬 스택이 뜨지 않음 | 검증을 통과로 처리하지 않는다. 원인을 고치거나 보고한다 |
| 선행 PR 미병합 | 진행하지 않고 어떤 PR 이 필요한지 알린다 |
| 스펙과 구현이 충돌 | 임의로 정하지 않는다. 쟁점과 선택지를 사용자에게 보고한다 |

## 테스트 시나리오

**정상 흐름.** "PR 3 진행해줘" 요청. 선행 PR 1 이 병합되어 있다. main 에서 브랜치를 만들고, implementer 가 S2, S4, S19 를 구현해 요약을 남긴다. verifier 가 MongoDB 참조가 남지 않았는지 확인하고 `e2e-verify` 로 저장과 상세 조회를 돌려 통과 판정을 낸다. PR 을 `simhani1/s-care` 로 올리고 링크를 전달한 뒤 멈춘다.

**반려 흐름.** verifier 가 상세 조회의 좌표 수가 저장한 수와 다르다고 반려한다. implementer 가 보고서의 재현 방법으로 원인을 찾아 고친다. verifier 가 같은 시나리오를 다시 돌려 통과시킨다.

**선행 미충족.** "PR 5 진행해줘" 요청인데 PR 4 가 병합되지 않았다. 구현을 시작하지 않고 PR 4 가 먼저 필요하다고 알린다.
